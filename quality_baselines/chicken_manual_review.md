# 小鸡需求文档人工基准评审报告

## 一、总体评价
当前文档已经描述了基础玩法循环，但还不适合直接进入完整开发和测试用例设计。最需要优先收敛的是“格子/马路/关卡”的核心术语、需求文档与数值文档中的筹码/难度/赔率/MAX_MUL映射，以及下注、扣款、获得、重进游戏等玩法专属边界规则。

- **文档质量评分：** C
- **评分原因：** 主流程方向可理解，但核心术语、数值映射、结算时机和异常边界仍存在高/中风险缺口，需要评审后补文档再进入完整开发。

## 评分档位说明
- **A：** 核心玩法、数值、边界、异常、验收标准完整清晰，仅剩低风险优化项，可直接进入开发和测试用例设计。
- **B：** 主流程和关键数值基本可开发，存在少量中风险缺口，但不影响主体方案开工。
- **C：** 主流程可理解，但存在高风险口径不一致、关键边界缺失、数值映射不清或验收标准不足，需补文档后再完整开发。
- **D：** 核心玩法、数值模型或结算链路无法理解/互相矛盾，开发和测试无法形成一致方案。

## 置信度说明
置信度表示“证据强度”，不是问题严重程度。
- **高：** 文档原文、表格或图片直接证明该问题存在。
- **中：** 多处内容强烈暗示该问题，但仍需策划确认。
- **低：** 基于文档缺失和经验提出的风险提醒。

## 优先处理事项
- **[高] 统一“格子/马路/关卡”的核心术语和单次点击后的状态流**
  - 责任建议：系统策划
  - 处理原因：这是点击开始后的核心骨架，若单次挑战单位不清，客户端表现、服务端状态和测试用例会各自按不同理解推进。
- **[高] 统一需求文档与数值文档的筹码、难度、概率、赔率、MAX_MUL 和最大赔付口径**
  - 责任建议：数值策划
  - 处理原因：当前跨文档数据无法直接验收，且极限难度倍率表出现千万级数值，必须在评审前明确正式配置、RTP关系和赔付边界。
- **[高] 补充下注、扣款、获得、提现/结算和重进游戏的关键时机**
  - 责任建议：系统策划
  - 处理原因：中台通用钱包或账务规范可以不在本文重复，但当前玩法必须说明何时扣款、何时获得、失败/通关/退出/重连时局内状态如何处理。

## 二、逐维度问题清单

### 【清晰度与完整性】
- **[严重程度：高] “格子、马路、关卡”的核心概念混用，点击开始后的挑战单位不清**
  - 现状描述：文档同时使用“每前进一格”“每次点击开始前进1格”“该马路永久封锁”“通过所有预设马路”等描述；从配图看更像一条条车道/马路承载倍率，而不是一个“马路里包含多个格子”的路径。当前无法判断玩家一次点击挑战的是一个格子、一条马路，还是一个关卡。
  - 证据来源：需求文档 / 1.2 “每前进一格”；需求文档 / 2.1 “每次点击「开始」，骆驼前进 1 格，抵达当前马路”；需求文档 / 2.1 “该马路永久封锁”；数值文档 / 3 “需要经过30个格子，因此每个难度有30个赔率”；图片中每个车道显示一个倍率。
  - 风险分析：这是核心玩法状态机的入口。如果挑战单位不统一，服务端 step_index、赔率表行号、客户端动画、失败/成功判定和测试用例都会错位。
  - 修改建议：统一术语并补一张状态表。建议定义“第N步/第N关=第N条马路/车道，对应赔率表第N行”；若确实存在“马路内多个格子”，需说明每条马路包含几个格子、倍率何时生效、失败概率作用在哪个层级。
  - 关注角色：系统策划
  - 置信度：高
  - 阻塞级别：阻塞开发
- **[严重程度：中] 结算文案没有明确扣款与获得的玩法时机**
  - 现状描述：文档写“模拟到账或对接真实支付”，但作为中台玩法文档，当前无需展开业务方钱包规范；真正缺的是玩法内何时扣款、何时只显示累计、何时真正获得奖励。
  - 证据来源：需求文档 / 3.4 提现流程：“确认后模拟到账（或对接真实支付）→ 游戏结束”；需求文档 / 2.1 “提现：立即获得当前总奖金”。
  - 风险分析：如果扣款、局内累计、失败清零、通关大奖、提现获得的时机不清，测试无法覆盖结算中断、重进游戏和最后一步奖励。
  - 修改建议：补充玩法级时机：开局扣款；每步成功只更新局内累计奖金；提现确认后发放；失败清零；通关大奖发放；结算失败或重进后的处理。
  - 关注角色：系统策划
  - 置信度：高
  - 阻塞级别：阻塞测试用例设计
- **[严重程度：中] “开始”按钮同时承担开局与继续挑战，状态机不完整**
  - 现状描述：“开始”既用于进入游戏，也用于继续挑战下一步；文档未说明在动画中、等待服务端结果、可提现、失败、通关、重进游戏等状态下按钮是否可点、是否置灰、显示什么文案。
  - 证据来源：需求文档 / 2.1 “点击「开始」进入游戏”；需求文档 / 2.1 “开始：挑战下一条马路”。
  - 风险分析：按钮状态不清会造成重复提交、误点、最后一步无下一关仍可点击等问题。
  - 修改建议：补充按钮状态表，至少覆盖未选筹码、未选难度、请求中、动画中、可提现、已失败、已通关、重进游戏后的按钮文案和禁用规则。
  - 关注角色：系统策划
  - 置信度：高
  - 阻塞级别：阻塞测试用例设计
- **[严重程度：低] 主角与题材在“小鸡、骆驼、中东商队”之间口径不统一**
  - 现状描述：文档和图片中的主角、玩法名、题材包装不一致，但这类情况可能是前期临时资源或题材未定，通常不影响核心开发。
  - 证据来源：需求文档 / 2.1 写“骆驼前进 1 格”；需求文档 / 4.1 写“卡通骆驼设计”；需求文档 / 4 段落55 写“先用默认的小鸡形象”；数值文档标题为“小鸡数值文档”；图片显示 CHICKEN ROAD 与小鸡 UI。
  - 风险分析：如果不标记，后续可能在文案、美术验收、测试命名和对外展示时产生口径混乱。
  - 修改建议：在需求开头补一句“当前小鸡资源为临时/正式资源，正式题材以 XX 为准”，并说明角色名、玩法名、美术资源替换是否影响验收。
  - 关注角色：策划
  - 置信度：高
  - 阻塞级别：建议优化

### 【逻辑一致性与数值平衡】
- **[严重程度：高] 筹码配置跨文档不一致**
  - 现状描述：需求文档的预设筹码与数值文档的下注挡位不是同一组值，无法判断哪个才是正式配置。
  - 证据来源：需求文档 / 表格1 写“预设筹码（3、5、10、20）”；数值文档 / 表格1 写“挡位1=100，挡位2=1000”。
  - 风险分析：下注金额直接参与扣款和奖金计算，跨文档不一致会导致前端显示、服务端配置、测试数据和数值评估无法对齐。
  - 修改建议：以数值文档或正式配置表为唯一来源，补充正式筹码列表、单位、最小/最大下注、业务方可配置范围和客户端展示格式；需求文档只引用配置字段。
  - 关注角色：数值策划
  - 置信度：高
  - 阻塞级别：阻塞开发
- **[严重程度：高] 难度、概率、赔率池和 MAX_MUL 没有建立可验收映射**
  - 现状描述：需求中写“被撞概率”“倍率池范围”，但没有说明概率作用于每一步、每条马路还是整局；“倍率池”也没有说明是随机池、固定表、范围上限还是展示文案。数值文档又使用难度1-4和MAX_MUL，映射关系缺失。
  - 证据来源：需求文档 / 表格2 四行难度均为“简单”，概率为 20%/35%/50%/65%；数值文档 / 表格2 使用“难度1-4”；数值文档 / 表格3 使用 MAX_MUL 24/62/103/176。
  - 风险分析：测试无法判断某一难度下第N步的正确倍率、失败概率、RTP组和MAX_MUL，数值模型也无法被程序化。
  - 修改建议：补充统一配置字段：difficulty_id、difficulty_name、display_name、step_index、per_step_odds、hit_probability_scope、force_hit_first、force_hit_non_first、max_mul、rtp_group、max_payout；并用一个难度给出完整示例。
  - 关注角色：数值策划
  - 置信度：高
  - 阻塞级别：阻塞开发
- **[严重程度：高] 极限难度倍率表存在最大赔付边界缺失**
  - 现状描述：数值文档中极限难度第30步倍率达到 66278475.57，需求文档还写通关会获得额外高额奖励，但没有最大赔付或超额处理规则。
  - 证据来源：数值文档 / 表格2：难度4 第30关倍率为 66278475.57；需求文档 / 3.4 写通关触发“超级大奖，获得额外高额奖励”。
  - 风险分析：千万级倍率叠加额外大奖，若没有每局最大赔付、大奖公式、超额处理和展示规则，开发和测试无法判断达到上限后的正确行为。
  - 修改建议：补充每局最大赔付、单局倍率上限、超级大奖计算公式、超出上限时的截断/拒绝/特殊提示规则，并提供数值模拟样例。
  - 关注角色：数值策划
  - 置信度：高
  - 阻塞级别：阻塞开发
- **[严重程度：中] 碰撞表现与爆炸倍数算法的展示关系不清**
  - 现状描述：默认功能逻辑由服务端实现，客户端只做表现；所以这里不是“分工不明确”问题，而是服务端结果给出后，客户端如何播放车辆刷新、通过、撞击、失败动画没有描述。
  - 证据来源：需求文档 / 3.2 “骆驼与车辆碰撞盒重叠即判定失败”；数值文档 / 4 “先随机一个本次被撞倍数，再结合每个关卡的必定被撞几率”。
  - 风险分析：表现和结算结果若无法对齐，会出现“画面没撞但结算失败”或“画面撞了但通过”的体验问题。
  - 修改建议：补充“服务端返回本步结果后，客户端按结果播放安全通过或被撞表现；碰撞盒、车辆速度、刷新频率仅用于表现，不改变结算结果”，并定义回包延迟时的loading/禁用状态。
  - 关注角色：系统策划
  - 置信度：高
  - 阻塞级别：阻塞测试用例设计
- **[严重程度：低] 最后一关后的“提现/继续/通关”抉择逻辑缺失**
  - 现状描述：文档写每通过1条马路后玩家可选择“提现”或“开始”，也写通过所有预设马路后触发超级大奖；但没有说明通过倒数第一步后是否仍出现提现/开始，还是直接进入通关。
  - 证据来源：需求文档 / 2.1 “每通过 1 条马路后，玩家可选择：提现 / 开始”；需求文档 / 2.1 “成功通过所有预设马路，触发超级大奖”。
  - 风险分析：最后一步如果仍显示“开始”会出现无下一关可挑战；如果直接结算又可能与“任意时刻可提现”冲突。
  - 修改建议：明确最后一步通过后的界面规则：自动通关结算、显示通关按钮、还是仍允许提现；并定义通关大奖与当前累计奖金的关系。
  - 关注角色：系统策划
  - 置信度：高
  - 阻塞级别：建议优化

### 【可测试性与验收标准】
- **[严重程度：高] 缺少下注、跳格、提现/结算的幂等和异常验收标准**
  - 现状描述：主流程只描述正常点击，没有说明重复点击、请求超时、服务端失败、结算中退出、重进游戏后的处理。
  - 证据来源：需求文档 / 2.1、3.4 只描述操作流程，未定义异常流程和边界。
  - 风险分析：测试无法覆盖快速点击开始、重复提现、提现后断线、服务端回包延迟、客户端重启恢复等高风险路径。
  - 修改建议：补充玩法状态机：未开局、已扣款、等待步进结果、可提现、结算中、已失败、已通关、已结算；每个状态定义可操作按钮、重复请求处理、错误提示和恢复规则。
  - 关注角色：系统策划
  - 置信度：高
  - 阻塞级别：阻塞测试用例设计
- **[严重程度：高] 重进游戏后的局内恢复规则缺失**
  - 现状描述：当前玩法存在“已扣款但未结算”“已通过若干步”“可提现但未确认”“结算中”等中间状态，但文档未说明断线、杀进程、切后台、跨设备登录后如何恢复。
  - 证据来源：需求文档和数值文档未说明断线、重连、重进游戏、结算中退出。
  - 风险分析：重进规则缺失容易产生玩家争议和测试盲区，尤其影响已扣款未获得的局。
  - 修改建议：补充重进规则：恢复当前局、强制失败、自动提现、或按服务端状态继续；同时定义当前步数、累计奖金、按钮状态、动画恢复和超时处理。
  - 关注角色：系统策划
  - 置信度：中
  - 阻塞级别：阻塞测试用例设计
- **[严重程度：中] 主观体验描述缺少可验收指标**
  - 现状描述：文档使用“快节奏”“轻量无负担”“高刺激”“跳动动画强化收益感知”等描述，但没有给出关键交互响应时间、动画时长、按钮反馈和失败/提现弹窗展示规则。
  - 证据来源：需求文档 / 1.1、1.2、3.3、3.4、4.3。
  - 风险分析：这类描述会让开发和策划在验收时依赖“感觉”，测试无法判定是否通过。
  - 修改建议：补充可验收指标，例如点击开始后多少毫秒内进入请求/动画反馈，被撞动画时长，奖金跳字时长，提现确认框出现时机，失败弹窗最短展示时间。
  - 关注角色：客户端策划
  - 置信度：中
  - 阻塞级别：建议优化
- **[严重程度：中] 关键边界条件缺失**
  - 现状描述：文档未说明下注上限、最后一格通关后是否还能提现、超出最大赔付、配置热更、活动关闭、历史局处理。
  - 证据来源：需求文档和数值文档未出现这些边界规则。
  - 风险分析：这些边界直接影响测试用例矩阵，遗漏后通常会在联调或灰度阶段暴露。
  - 修改建议：补充边界规则表，覆盖最大下注、最大赔付、最后一格、重进游戏、活动下线、配置热更和历史局处理。
  - 关注角色：系统策划
  - 置信度：中
  - 阻塞级别：阻塞测试用例设计

### 【跨系统影响与兼容性】
未发现需要在本需求文档中额外阻塞的通用跨系统问题。钱包、余额、机型兼容、运营后台、埋点、日志、GM等若已有中台通用规范，不在本文重复列为缺陷；本轮相关风险已收敛到“扣款/获得时机、最大赔付、重进游戏、配置热更和历史局处理”等玩法专属规则。

### 【安全性与反作弊】
- **[严重程度：中] 结算重复提交和并发操作的玩法表现规则未写入验收**
  - 现状描述：底层幂等、频控、防重放可以由通用服务保障，但玩法文档仍未定义玩家在结算中重复点击开始/提现、超时重试、已结算后再次操作时看到什么。
  - 证据来源：需求文档 / 3.4 提现流程未定义重复确认、超时重试、结算中再次点击开始/提现的处理。
  - 风险分析：即使服务端拒绝重复请求，客户端表现和错误映射不清也会导致测试无法验收、玩家误解为卡单或丢奖励。
  - 修改建议：补充结算中按钮禁用、重复点击提示、超时提示、重试入口、已结算局再次操作的前端表现和服务端错误映射。
  - 关注角色：系统策划
  - 置信度：高
  - 阻塞级别：阻塞测试用例设计

### 【用户体验与游戏性】
- **[严重程度：中] UI显示“被击中的概率”但未给出实际值与变化规则**
  - 现状描述：界面上有“被击中的概率”文案，但文档没有说明展示的是当前步失败概率、累计失败概率、难度说明，还是占位文案。
  - 证据来源：图片 / 需求文档 image1 与数值文档 image1 均有“被击中的概率”文案；需求和数值表未定义 UI 展示哪个概率。
  - 风险分析：如果展示概率与真实算法不一致，玩家会认为玩法不透明；如果暂不展示数值，也需要明确文案和占位状态。
  - 修改建议：明确每一步展示的是当前步失败概率、累计失败概率、难度说明，还是不展示精确值；若不展示精确概率，应修改文案避免误导。
  - 关注角色：数值策划
  - 置信度：高
  - 阻塞级别：阻塞测试用例设计
- **[严重程度：中] 提现确认框与快节奏定位之间缺少策略说明**
  - 现状描述：文档要求提现弹出确认框，但游戏定位是快节奏、轻量无负担；确认策略没有按金额、首次操作或业务方配置分层。
  - 证据来源：需求文档 / 3.4 “点击提现→弹出确认框”；需求文档 / 1.1、1.2 “快节奏”“轻量无负担”。
  - 风险分析：每次提现都确认会打断核心循环；不确认又可能误点造成争议。
  - 修改建议：定义确认策略，例如低金额一键提现，高金额或首次提现二次确认；确认框必须显示当前获得金额和取消返回后的局内状态。
  - 关注角色：策划
  - 置信度：中
  - 阻塞级别：建议优化
- **[严重程度：低] 失败清零后的连续再玩体验缺少承接**
  - 现状描述：失败后提供“再来一局”按钮，但文档未说明是否沿用上次筹码和难度、是否跳过准备界面、是否给出失败后的正向引导。
  - 证据来源：需求文档 / 3.4 “失败结算：提供「再来一局」按钮”；需求文档 / 3.1 “默认继承上次选择”。
  - 风险分析：失败清零本身挫败感强，如果重开路径仍繁琐，会降低轻量玩法的连续体验。
  - 修改建议：明确“再来一局”是否默认沿用上次筹码和难度，是否一键开局；失败界面可补充下一局潜在收益或轻量鼓励文案。
  - 关注角色：策划
  - 置信度：中
  - 阻塞级别：建议优化

## 跨文档一致性问题
- **[严重程度：高] 需求文档与数值文档的筹码、难度、概率、倍率、MAX_MUL未统一**
  - 现状描述：需求文档给了一套面向玩法说明的筹码/难度/概率，数值文档给了另一套下注挡位、难度1-4、赔率表和MAX_MUL，缺少一张正式映射表。
  - 证据来源：需求文档表格1/2 + 数值文档表格1/2/3。
  - 风险分析：配置源不统一会直接影响开发读取配置、测试造数和策划验收。
  - 修改建议：建立一张正式配置映射表，并在需求文档中引用配置表而不是重复写示例值。
  - 关注角色：数值策划
  - 置信度：高
  - 阻塞级别：阻塞开发

## 三、核心测试点建议
- **功能验证：** 筹码选择、难度选择、30步推进、每步赔率展示、失败清零、提现获得、通关大奖、最后一步处理、再来一局、配置热更后的新局读取。
- **异常操作：** 开始/提现快速连点、弱网超时、断网后重进、进程切后台、服务端回包失败、结算中退出、最后一格结算。
- **兼容性：** 只验证当前玩法专属UI在目标横屏比例下的按钮遮挡、弹窗层级、返回键和重进恢复表现；通用机型兼容按平台规范执行。
- **安全专项：** 聚焦玩法层面的重复结算、并发提现、修改步数/难度/倍率、重进恢复绕过结算；底层钱包和日志审计按通用规范回归。
- **回归影响：** 当前局状态、扣款/获得时机、配置版本、历史未结算局、失败清零、通关大奖。
- **性能与稳定性：** 高频开局、连续步进、结算中断恢复、赔率表热更新、动画资源加载。
- **用户体验：** 概率显示口径、按钮状态反馈、提现确认策略、失败提示、大奖表现、断线/重进提示、再来一局路径。
