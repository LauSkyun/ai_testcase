# 需求文档分析报告

## 一、总体评价
文档整体描述了核心玩法循环，但需求文档与数值文档在核心结算公式、概率生成模型和下注配置上存在严重冲突，导致主流程无法形成一致的实现方案。需数值策划与系统策划对齐后重新输出统一版本。

- **文档质量评分：** C
- **评分原因：** 主流程可理解，但存在核心结算公式与数值表定义冲突、概率模型双轨冲突等高风险缺口，且断线恢复、提现幂等等关键边界缺失，需补充后再完整开工。

## 优先处理事项
- **[高] 结算公式与数值表定义冲突（连乘 vs 累计）**
  - 责任建议：数值策划
  - 处理原因：若按连乘计算，结果将远超MAX_MUL上限，导致数值模型崩溃和严重超发；若按累计计算，则需求文档公式错误，开发无法实现。
- **[高] 概率生成模型双轨冲突（离散映射 vs Crash算法）**
  - 责任建议：数值策划
  - 处理原因：两套概率逻辑完全互斥，程序无法同时实现，测试无法编写用例。；两套概率逻辑互斥，且关键难度参数缺失，无法落地。
- **[中] 总关卡数与“超级大奖”结算边界不清**
  - 责任建议：系统策划
  - 处理原因：若第30格包含在常规结算中，则与“额外高额奖励”描述冲突；若不包含，则超级大奖的具体数值/公式缺失，导致结算链路无法闭环。

## 二、逐维度问题清单
### 【清晰度与完整性】
- **[严重程度：中] 总关卡数与“超级大奖”结算边界不清**
  - 现状描述：需求文档提及“成功通过所有预设马路，触发超级大奖”，数值文档明确为30个格子。但未说明第30格是包含在常规倍率结算中，还是额外发放“超级大奖”。
  - 证据来源：小鸡.docx / 2.1 完整游戏流程（通关阶段）；小鸡数值文档.docx / 3. 难度选择（30个格子）
  - 风险分析：1、若第30格包含在常规结算中，则与“额外高额奖励”描述冲突；2、若不包含，则超级大奖的具体数值/公式缺失，导致结算链路无法闭环。
  - 修改建议：1、明确第30格的结算逻辑。若为额外奖励，需补充超级大奖的数值公式（如固定金额、下注额的N倍或奖池比例）；2、若为常规结算，需删除“额外高额奖励”的歧义描述。
  - 关注角色：系统策划
  - 置信度：高
  - 阻塞级别：阻塞开发
- **[严重程度：中] 下注筹码配置跨文档冲突**
  - 现状描述：需求文档明确下注筹码为3、5、10、20（或业务自定义），而数值文档示例为100、1000。
  - 证据来源：小鸡.docx / 表格1（下注与筹码）；小鸡数值文档.docx / 表格1（下注规则）
  - 风险分析：前后端配置不一致，导致下注接口校验失败或UI展示错误。
  - 修改建议：统一筹码配置表，明确是否支持自定义输入及边界限制（如最小/最大值）。
  - 关注角色：系统策划
  - 置信度：高
  - 阻塞级别：阻塞测试用例设计
- **[严重程度：中] 难度枚举映射与MAX_MUL动态配置规则缺失**
  - 现状描述：1、需求文档使用“简单/中等/困难/极限”，数值文档使用“难度1/2/3/4”及“24/62/103/176倍盘”。未说明MAX_MUL是否支持运营后台动态热更。；2、局内有多次点击继续的抉择，但文档未定义局内状态机的断线恢复规则。
  - 证据来源：小鸡.docx / 表格1（难度系统）；小鸡数值文档.docx / 表格3（MAX_MUL配置）；小鸡.docx / 2.1 完整游戏流程（抉择阶段）
  - 风险分析：1、前后端难度枚举名称不一致，易导致配置错误；2、未明确配置方式可能导致后续运营调整困难。；3、玩家在第15格点击“继续”后断线，重连后是自动结算、恢复在第15格等待点击，还是直接判负？规则缺失会导致服务端状态机设计遗漏。
  - 修改建议：1、建立难度枚举映射表（简单=难度1=24倍盘等），并明确MAX_MUL和必爆概率的配置方式（代码硬编码还是后台配置表）。；2、补充局内状态机的断线恢复规则（如：保留当前进度和倍率，重连后恢复抉择界面，或超时自动提现/判负）。
  - 关注角色：系统策划
  - 置信度：中
  - 阻塞级别：阻塞测试用例设计
- **[严重程度：低] 角色形象术语混淆（骆驼/小鸡）**
  - 现状描述：需求文档正文大量使用“骆驼”，但UI图片和数值文档均为“小鸡”，且段落55提到“先用小鸡，后续替换”。
  - 证据来源：小鸡.docx / 4.1 核心形象（卡通骆驼设计）；小鸡.docx / 段落55；图片1-8
  - 风险分析：易导致测试用例和美术资源验收标准混乱，开发可能误用资源。
  - 修改建议：统一文档术语，或在概述中明确“小鸡为当前占位符，骆驼为后续美术替换目标”，避免误解。

  - 置信度：高
  - 阻塞级别：建议优化

### 【逻辑一致性与数值平衡】
- **[严重程度：高] 概率生成模型双轨冲突（离散映射 vs Crash算法）**
  - 现状描述：1、需求文档表格2给出了“简单”难度下“被撞概率与倍率”的离散映射（如20%->1.03x），而数值文档采用的是类似Crash的连续随机爆炸倍数算法（结合首撞/非首撞必爆概率）。；2、需求文档表格2给出了离散概率映射，数值文档采用Crash算法。且需求文档仅提供了“简单”难度的参数，中等/困难/极限缺失。
  - 证据来源：小鸡.docx / 表格2（难度数值参考）；小鸡数值文档.docx / 4. 撞击概率计算；小鸡.docx / 表格2；小鸡数值文档.docx / 4. 撞击概率计算
  - 风险分析：1、两套概率逻辑完全互斥，程序无法同时实现，测试无法编写用例。；2、两套概率逻辑互斥，且关键难度参数缺失，无法落地。
  - 修改建议：1、废弃需求文档表格2的离散模型，统一采用数值文档的Crash算法，并补全中等/困难/极限难度的MAX_MUL和必爆概率参数。；2、废弃需求文档表格2，统一采用Crash算法，并补全所有难度的MAX_MUL和必爆概率参数。
  - 关注角色：数值策划
  - 置信度：高
  - 阻塞级别：阻塞开发
- **[严重程度：高] 结算公式与数值表定义冲突（连乘 vs 累计）**
  - 现状描述：需求文档定义公式为“总奖金 = 下注金额 × Π(已通过马路倍率)”（连乘），但数值文档表2提供的30个关卡数值（如难度1第30关为23.9，接近MAX_MUL 24）明显是“累计总倍率”。
  - 证据来源：小鸡.docx / 3.3 奖金计算系统（公式）；小鸡数值文档.docx / 3. 难度选择（表2）
  - 风险分析：1、若按连乘计算，结果将远超MAX_MUL上限，导致数值模型崩溃和严重超发；2、若按累计计算，则需求文档公式错误，开发无法实现。
  - 修改建议：1、明确表2是单格倍率还是累计倍率。若是累计，修改需求文档公式为“总奖金 = 下注金额 × 当前累计倍率”；2、若是单格，重新提供符合MAX_MUL上限的单格倍率表。
  - 关注角色：数值策划
  - 置信度：高
  - 阻塞级别：阻塞开发

## 三、核心测试点建议
### 功能验证
- 验证下注、前进、提现、失败清零、通关的主流程
- 验证不同难度下的倍率增长是否符合数值表
- 验证UI展示的概率与实际结算概率是否一致
### 异常操作
- 局内断线重连，验证进度和倍率是否恢复
- 弱网环境下重复点击提现按钮，验证是否重复发奖
- 结算中退出游戏，验证资金是否正确到账
### 兼容性
- 不同分辨率下UI布局适配，特别是底部控制面板和倍率显示
- 低端机型下30格动画和Crash算法的性能表现
### 安全专项
- 篡改客户端倍率或概率参数，验证服务端是否拦截
- 并发请求提现接口，验证幂等性
- 验证最大赔付上限（MAX_MUL）是否被严格限制
### 回归影响
- 无
### 性能与稳定性
- Crash算法在高并发下的随机数生成性能
- 长时间挂机或多次重连后的内存泄漏检查
### 用户体验
- 新手引导是否清晰说明30格上限和提现机制
- 失败清零的挫败感反馈是否合理，是否有补偿或安慰机制
