# 三种审查方案横向评估

## 评估对象

本次评估的三种方案分别对应：

1. 单模型分析输出报告
2. 双模型分别分析，再整合输出报告
3. 主模型分析，副模型评审 + 补充 + 候选成稿输出报告

在当前项目里，大致可映射为：

1. 单模型：早期单模型主分析链路，当前可类比 `fast / strict` 的“单报告主链”
2. 双模型分别分析再整合：`fusion`
3. 主模型分析 + 副模型评审补充：`dual_pass`

## 样本与证据边界

本次分析主要参考了三类本地证据：

- 历史产物形态与当前代码结构
- `fusion` 代表样本：如 `20260603_104134`
- `dual_pass` 近期样本：如 `20260622_180139`、`20260622_180957`

同时补充了当前 `reports/` 的粗粒度统计：

- `single_or_legacy`：95 份
- `fusion`：33 份
- `dual_pass`：59 份
- `dual_pass_candidate`：9 份

对 `dual_pass` 的索引页统计粗看：

- `recommended`：9
- `fallback_pipeline`：55
- `candidate_unavailable`：4

注意：

- 这些样本并不是严格同一批文档、同一阶段、同一提示词下的 A/B 测试
- 因此它们更适合做“架构层趋势判断”，不适合机械做精确分数结论

## 总结结论

如果只看“当前最稳的默认交付链路”，方案 1 仍然最省心。  
如果看“长期最值得投入的方向”，方案 3 明显优于方案 2，也优于纯方案 1。  
如果看“问题覆盖最大化但不考虑报告臃肿和后处理成本”，方案 2 一度最激进，但综合收益已经不如方案 3。

最终建议：

- 不建议回退到方案 2 作为主方向
- 方案 1 适合作为保底基线
- 方案 3 应继续作为主迭代方向，目标是让 candidate 最终替代 pipeline

## 一、方案 1：单模型分析输出报告

### 工作方式

- 同一模型读取文档、完成分析、直接输出一份最终报告
- 没有第二模型复核，也没有双报告合并

### 优点

- 链路最短，稳定性最好
- 没有“双报告 merge”带来的膨胀和歧义
- 问题来源最清晰，追踪成本最低
- 开发和维护复杂度最低
- 运行成本最低

### 缺点

- 问题覆盖完全受单次模型输出上限约束
- 容易漏掉边界条件、异常流程、跨文档冲突
- 一旦主模型把某个根因漏掉，系统没有补救层
- 对同类问题的“严重度纠偏”“问题去重”“表达修正”能力较弱

### 从报告质量看

优点：

- 通常结构干净
- 不容易出现“标题、lineage、advice、candidate”之间的协议冲突

缺点：

- 一旦主模型误判，就会原样进入最终报告
- 很难自动提高 recall

### 综合评价

- 覆盖全面性：中
- 稳定性：高
- 可追踪性：高
- 报告可读性：高
- 默认直出安全性：高
- 后续提升空间：中
- 综合维护成本：低

### 适用场景

- 文档质量本身较高
- 更重视稳定交付和低成本
- 更在意“少出怪问题”，而不是“尽可能多补漏”

## 二、方案 2：双模型分别分析，再整合输出报告

### 工作方式

- 主模型先分析一份
- 副模型在自己的输入和 prompt 下独立再分析一份
- 最后把两份报告进行 merge

### 优点

- 理论上的问题覆盖率最高
- 副模型更容易发现主模型没提到的独立问题
- 对 recall 的提升最直接

### 缺点

- 两个模型输入不完全一致时，容易造成“分析前提不一致”
- 两份完整报告 merge 的复杂度极高
- 近义根因、不同命名、不同严重度、不同分组方式，都会放大后处理难度
- 报告很容易臃肿
- 同一根因会以不同标题、不同维度重复出现
- 最终报告虽然“信息更多”，但不一定“更好用”

### 从产物看出的典型问题

参考 `fusion` 代表样本 `20260603_104134`：

- 最终 `findings = 25`
- 其中 `secondary` 来源问题多达 `14`
- `fusion_summary.added_unique_findings = 14`

这类结果说明：

- `fusion` 确实能显著提高补漏数量
- 但也很容易把最终报告推向高密度、高膨胀状态

从历史实践看，方案 2 的核心问题不在“副模型没价值”，而在：

- 副模型是“重新写一份自己的报告”
- 系统再试图把“两套世界观”合成一套最终稿

这一步非常贵，而且不稳定。

### 综合评价

- 覆盖全面性：高
- 稳定性：低到中
- 可追踪性：中
- 报告可读性：低到中
- 默认直出安全性：低
- 后续提升空间：低到中
- 综合维护成本：高

### 适用场景

- 只追求 recall，接受后续人工筛选
- 可容忍报告膨胀
- 不要求系统自己把最终稿整理得很干净

### 当前判断

方案 2 是“补漏最猛”的方案，但不是“最优最终报告方案”。  
它更像一个强 recall 实验方向，而不是一个适合长期作为默认输出的主链路。

## 三、方案 3：主模型分析，副模型评审 + 补充 + 候选成稿

### 工作方式

- 主模型先产出首版报告
- 副模型不再独立写第二份完整首审报告
- 副模型基于同一份共享事实输入 + 主模型首版报告，完成三件事：
  - 评估主模型质量
  - 补充主模型遗漏
  - 生成候选最终稿

### 这套设计为什么优于方案 2

核心变化有两个：

1. 主副模型共享同一事实底座  
2. 副模型从“重新分析一遍”改成“围绕主模型做复核和候选成稿”

这两个变化的价值非常大：

- 降低了输入不一致导致的漂移
- 降低了“两份独立世界观 merge”的复杂度
- 让副模型更像“审校 + 补漏 + 候选编辑”，而不是“第二个作者”

### 已经体现出来的优势

以 `20260622_180139` 为例：

- `traceability_status = complete`
- `raw_structure_change = true`
- `structure_change_explained_by_lineage = true`
- `candidate_structure_drift = false`
- `materially_changed_count = 4`

说明当前 `dual_pass` 已经具备以下能力：

- 能区分“结构变化”和“不可追踪漂移”
- 能看见 pipeline 与 candidate 的共享问题是否被明显改写
- 能把副评审补充问题带来源字段落到最终报告
- candidate 不合格时，系统能自动回退到 pipeline

这比方案 2 的“先 merge 再赌结果对不对”安全很多。

### 当前仍然存在的缺点

虽然方向正确，但方案 3 还没完全成熟。  
参考 `20260622_180957`：

- `traceability_status = partial`
- `candidate_structure_drift = true`
- `readiness_conflict = true`
- `unmapped_candidate_issue_ids = ["MISSED_RESPIN_END"]`

这说明副模型仍会偶发：

- 少写 lineage
- advice 和 candidate 结构对不上
- 把补漏问题吸收进 kept finding，却不写 `added`
- 把根本冲突写轻
- 把大问题写得过度膨胀

不过和方案 2 不同的是：

- 这些问题现在大多能被系统诊断出来
- 坏 candidate 会被阻断，不会默默顶掉 pipeline

也就是说，方案 3 当前的主要问题是“candidate 还不够稳定”，而不是“系统看不出来 candidate 坏了”。

### 综合评价

- 覆盖全面性：高于方案 1，接近方案 2
- 稳定性：中到高，显著优于方案 2
- 可追踪性：中到高，成熟后潜力最高
- 报告可读性：中到高
- 默认直出安全性：当前中，成熟后高
- 后续提升空间：高
- 综合维护成本：中

### 适用场景

- 既想提高问题覆盖率
- 又想保留系统级回退、安全门槛和报告可追踪性
- 希望未来 candidate 真正替代 pipeline

## 四、三种方案横向打分

以下评分是基于当前项目状态的工程判断，满分 5 分：

| 维度 | 方案1 单模型 | 方案2 双模型独立分析后整合 | 方案3 主分析 + 副评审补充 |
|---|---:|---:|---:|
| 问题覆盖全面性 | 3 | 5 | 4.5 |
| 输出稳定性 | 4.5 | 2.5 | 4 |
| 问题来源可追踪性 | 4.5 | 3 | 4 |
| 最终报告可读性 | 4 | 2.5 | 4 |
| 默认直出安全性 | 4.5 | 2.5 | 4 |
| 后处理复杂度可控性 | 5 | 2 | 4 |
| 长期优化空间 | 3 | 3 | 5 |
| 综合工程性价比 | 4 | 2.5 | 4.5 |

## 五、从关键维度做“环评”

### 1. 问题覆盖的全面性

结论：

- 方案 2 和方案 3 都明显优于方案 1
- 但方案 2 的优势来自“第二份独立分析”，代价是信息噪声更大
- 方案 3 的优势来自“围绕主报告做 targeted review”，补漏更聚焦

判断：

- 如果目标只是“找更多问题”，方案 2 最激进
- 如果目标是“找更多有价值的问题，并且能进入最终成稿”，方案 3 更优

### 2. 稳定性

结论：

- 方案 1 最稳
- 方案 3 当前已经明显优于方案 2
- 方案 2 的不稳定，主要来自两份完整报告的合并

判断：

- 方案 3 的 candidate 还不够稳
- 但方案 3 整个系统已经稳，因为它有：
  - shared input
  - advice 诊断
  - traceability 诊断
  - candidate gate
  - pipeline fallback

也就是说：

- 方案 3 当前是“candidate 不总稳，但系统整体稳”
- 方案 2 更像是“系统本身就不太稳”

### 3. 报告可读性与最终成稿质量

结论：

- 方案 1 通常最干净
- 方案 2 最容易臃肿
- 方案 3 在方向上最接近“既完整又可读”

当前状态：

- 方案 3 的 pipeline 版已经明显比旧 fusion 更可控
- candidate 版有时能优于 pipeline
- 但仍存在“过度合并”“主问题膨胀”“协议未写全”这类波动

### 4. 可追踪性

结论：

- 方案 1 天然最简单
- 方案 2 最难追
- 方案 3 是唯一认真把“血缘追踪”做成系统能力的方案

这是方案 3 最重要的长期价值之一：

- 它不只是要“多找问题”
- 还要回答“这个问题从哪来、为什么改、有没有越改越漂”

### 5. 工程维护成本

结论：

- 方案 1 最低
- 方案 2 最高
- 方案 3 中等，但收益最高

原因：

- 方案 2 需要长期为“两个模型写两份完整报告，再 merge”买单
- 方案 3 虽然协议复杂，但复杂度更集中、更可诊断，也更容易继续优化

## 六、最终建议

### 结论一：三种方案里，长期最优方向是方案 3

理由：

- 它兼顾了补漏能力和报告可控性
- 它通过 shared input 避免了方案 2 最大的前提漂移问题
- 它通过 lineage / readiness / block reasons / fallback，把“坏 candidate”拦在系统里，而不是直接放给用户
- 它是唯一有机会真正让 candidate 取代 pipeline 的架构

### 结论二：不建议回退到方案 2 作为主线

理由：

- 方案 2 的 recall 价值是有的
- 但最终报告层面的噪声、臃肿、重复、合并成本太高
- 从长期工程性价比看，不如继续把方案 3 打磨成熟

### 结论三：方案 1 仍然应该保留为基线和回退思路

理由：

- 方案 1 依旧是最稳定、最可控、最容易解释的保底方案
- 它适合做：
  - 对照基线
  - 异常回退
  - 判断“副模型到底有没有真正带来净增益”

## 七、目前阶段的最现实判断

如果今天就要做“默认最终输出”的决策：

- 不建议选方案 2
- 也不建议完全只停留在方案 1
- 最合理的是：
  - 继续以方案 3 为主迭代方向
  - 当前默认仍保留 pipeline fallback
  - 继续围绕 candidate 的协议稳定性、lineage 完整性、正文收敛性做收敛

换句话说：

- 方案 1 是当前最稳的保底形态
- 方案 3 是当前最值得继续投资、也最有机会成为最终默认形态的方案
- 方案 2 已经完成了它的历史使命，但不适合作为长期默认主架构

## 八、一句话结论

从“问题覆盖、稳定性、可追踪性、最终报告质量、长期工程性价比”综合看：

**方案 3（主模型分析 + 副模型评审补充）是当前最优方向；方案 1 适合作为稳定基线；方案 2 不建议继续作为主方案。**
