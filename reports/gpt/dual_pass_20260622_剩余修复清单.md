# dual_pass 剩余修复清单（基于 20260622_180139 / 20260622_180957）

## 结论

`20260622_180139` 说明这一轮代码修复已经开始生效：

- `raw_structure_change = true`
- `structure_change_explained_by_lineage = true`
- `candidate_structure_drift = false`
- `materially_changed_count = 4`

也就是说：

- “结构变化已被 lineage 解释”不再误报为 drift
- “共享问题被重大改写”已经能被摘要页显式暴露

但 `20260622_180957` 又暴露出副模型协议和正文收敛仍不稳定：

- `traceability_status = partial`
- `candidate_structure_drift = true`
- `readiness_conflict = true`
- `unmapped_candidate_issue_ids = ["MISSED_RESPIN_END"]`

当前系统已经能识别并阻断这类坏 candidate，这很好；但要让 `candidate` 真正可默认切换，还需要继续收敛下面这些缺口。

## P0：必须优先修

### 1. 副模型“补漏已合并 / 已吸收”与实际 candidate 结构不一致

现象：

- 在 `20260622_180957` 中，副评审 `review_notes` 说“RESPIN 结束机制冲突已合并进 RESPIN_FORMULA”
- 但最终 candidate 里它仍然以独立 finding 存在：`MISSED_RESPIN_END`
- 同时 `candidate_lineage.added = []`

影响：

- advice、candidate、lineage 三者互相打架
- 代码只能判定为 `partial traceability`
- 这类 candidate 即使内容看起来“像对的”，也不能安全默认直出

建议修复：

- 在 secondary prompt 中进一步硬化规则：
  - 只要 `missed_findings` 被吸收到 kept finding，必须在 `candidate_lineage.kept[*]` 里显式写 `absorbed_missed_issue_ids`
  - 只要 `missed_findings` 仍以独立 finding 出现在 candidate，必须写入 `candidate_lineage.added`
- 在 advice 归一化阶段增加一致性校验：
  - 若 `review_notes` 声称“已合并/已吸收”，但 candidate 中仍存在同源独立问题，追加 `candidate_block_reasons += advice_candidate_structure_mismatch`
  - 若 `missed_findings` 在 candidate 中实际落成独立问题，但 `added` 为空，自动标记 `candidate_lineage_coverage_incomplete`

验收标准：

- 同一 missed finding 不再出现“文字说已合并、结构却没合并”的状态
- candidate 中凡是新增独立问题，`added` 必有映射

### 2. 多症状主问题仍然过度膨胀

现象：

- `20260622_180139` 的 `RESPIN_FORMULA_CONFLICT` 虽然已经改成分点展示，但仍把公式歧义、风控死锁、UI高亮、123列定义、推展机制都揉进一条

影响：

- 问题可读性下降
- 主问题边界变模糊
- 后续再做 severity、merge、traceability 都更容易失真

建议修复：

- 增加“单 finding 症状收敛上限”：
  - 若 `current_state` 编号点超过 5 条，触发二次归并
  - 优先保留真正支撑标题根因的 2-4 条
  - 与主根因弱相关的说明迁移到 `quality_notes` 或拆回其他 kept finding
- 对多症状 finding 增加字段级分类后处理：
  - 公式/规则冲突
  - 触发条件定义
  - 表现层验收
  - 异常恢复
  - 安全/服务端权威性

验收标准：

- 高风险主问题的 `current_state / risk / suggestion` 保持分点，但每个字段不再无限膨胀
- 一个 finding 尽量只承载一个稳定根因

### 3. 根本冲突问题被错误降级

现象：

- `20260622_180957` 中，`MISSED_RESPIN_END` 的内容明显是核心规则互斥
- 但最终落成 `severity = 中`、`blocking = 阻塞测试用例设计`

影响：

- 副模型会把真实高风险问题“写出来但写轻了”
- candidate 质量表面可读，实质判断偏弱

建议修复：

- 给 `build_dual_pass_secondary_finding()` 增加 severity floor：
  - 若 `missed_findings` 的原始描述含“根本冲突 / 无法由同一实现满足 / 阻塞开发 / RTP 直接变化 / 结算逻辑互斥”等强信号
  - 且 candidate 侧把它降成 `中` 或更低，则记录 `severity_conflict_note`
- 若副模型把这类问题从高风险降级，必须在 `review_notes` 写出具体依据；否则默认沿用 missed finding 原始严重度

验收标准：

- 类似 RESPIN 结束机制这类互斥问题，不再被轻率降成“中风险验收问题”

## P1：本轮建议继续做

### 4. advice 与 candidate 的结构声明需要对账

现象：

- 现在系统能看出 lineage 不完整，但还不能明确指出“是哪一种结构性自相矛盾”

建议修复：

- 新增诊断项：
  - `advice_candidate_structure_mismatch`
  - `advice_claimed_absorbed_but_materialized_separately`
  - `advice_claimed_added_but_not_materialized`

价值：

- 后续看索引页时，不用翻 `secondary_raw_model_response.txt`
- 直接就能知道 candidate 被拦下的具体结构原因

### 5. 同一根因跨运行的命名稳定性仍偏弱

现象：

- 同类 RESPIN 问题在不同运行里仍会出现 `RESPIN_FORMULA` / `RESPIN_FORMULA_CONFLICT` 这类命名漂移

影响：

- 横向比较时仍有理解成本
- 长期不利于做“样本级稳定性评估”

建议修复：

- 在 dual_pass 内引入更保守的 canonical issue id/title 归一化
- 仅对高频核心根因做受控映射，不做全量自动改写

验收标准：

- 同一文档复跑时，核心问题的 issue_id/title 不再频繁换壳

### 6. fallback 原因已经很多，但优先级表达还不够强

现象：

- `candidate_block_reasons` 已经很全，但没有区分“协议错误”和“内容质量一般”

建议修复：

- 增加 block reason 分层：
  - protocol_blockers
  - traceability_blockers
  - quality_blockers
  - readiness_blockers

价值：

- 能更快判断当前样本是“模型没按协议输出”，还是“candidate 内容本身还不行”

## P2：后续再做

### 7. 进一步提升 candidate 直出率

当前历史样本粗看：

- `dual_pass` 最终样本中
  - `recommended = 9`
  - `fallback_pipeline = 55`
  - `candidate_unavailable = 4`

这说明：

- 当前 `dual_pass` 的“安全回退机制”已经可用
- 但 `candidate` 作为默认最终输出的成熟度仍然不高

建议：

- 先解决 P0 / P1 的协议与结构问题
- 再评估是否放宽 candidate 默认切换门槛

## 推荐实施顺序

1. 先修“合并声明和实际结构不一致”
2. 再修“根本冲突问题被错误降级”
3. 再收敛“多症状主问题过度膨胀”
4. 然后补 advice/candidate 对账诊断
5. 最后再做 issue_id/title 稳定化

## 当前判断

`dual_pass` 的系统侧诊断能力已经进入“能拦坏稿”的阶段，但还没进入“candidate 可稳定默认直出”的阶段。

接下来最关键的，不是继续美化报告，而是继续把：

- 协议一致性
- 结构可追踪性
- 严重度判断纪律

这三件事先钉死。
