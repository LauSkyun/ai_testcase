# 需求文档分析报告

## 一、总体评价
文档整体描述了‘小鸡过马路’的休闲博弈玩法，主流程（下注-前进-提现/失败）逻辑清晰，题材包装与UI示意较为完整。但核心结算链路、资金流转、胜负判定边界存在明显缺失，且需求文档与数值文档在难度、倍率、概率的映射上存在严重冲突，需优先修复高风险缺口。

- **文档质量评分：** C
- **评分原因：** 主玩法循环可理解，但存在资金链路定义模糊、客户端/服务端胜负判定边界冲突、跨文档数值映射断裂等高风险缺口，需补充核心结算规则与异常恢复机制后方可完整开工。

## 优先处理事项
- **[中] 难度、倍率与概率的跨文档映射断裂**
  - 责任建议：数值策划
  - 处理原因：开发和测试无法确定真实的赔率表和概率公式，主流程无法编译和验收。；通关结算逻辑缺失，无法实现‘额外高额奖励’的发放，可能导致通关后收益不符合预期。

## 二、逐维度问题清单
### 【清晰度与完整性】
- **[严重程度：中] 总奖金计算公式中的倍率定义不明确**
  - 现状描述：1、需求文档公式为“总奖金 = 下注金额 × Π(已通过马路倍率)”，暗示每个格子的倍率需要连乘；2、但数值文档中倍率表数值（如难度1：1.01, 1.03, 1.06... 23.9）增长特征符合累积倍率，且UI中提现金额显示为20×1.03=20.6，也支持累积倍率。文档未明确说明倍率是每格独立倍率还是累积总倍率，将导致结算逻辑实现错误。
  - 证据来源：小鸡.docx / 3.3 奖金计算系统；小鸡数值文档 / 表格2；小鸡.docx / 图片解析（提现20.6 USD）
  - 风险分析：1、若按连乘实现，总奖金将指数爆炸，与数值文档设计不符；2、若按累积倍率，需求文档公式需修正，测试验收无法进行。
  - 修改建议：统一定义为：'总奖金 = 下注金额 × 当前所在格子的累积倍率'，并在数值文档中明确标注表格内的倍率为累积倍率。需求文档公式应同步更新。
  - 关注角色：待定
  - 置信度：高
  - 阻塞级别：阻塞开发
  - 问题来源：副评审补充 (deepseek-v4-pro)
- **[严重程度：中] 难度、倍率与概率的跨文档映射断裂**
  - 现状描述：1、《小鸡.docx》中简单难度的倍率池仅有4个数据（1.03x-1.17x），概率为20%-65%；2、而《小鸡数值文档》中难度1有30个关卡赔率（1.01-23.9），且采用MAX_MUL=24的CRASH公式。两者对难度、倍率、概率的定义完全脱节。；3、需求文档提到‘成功通过所有预设马路，触发超级大奖，获得额外高额奖励’，但数值文档中仅提供了30个关卡的倍率，没有‘超级大奖’的额外奖励公式或配置。
  - 证据来源：小鸡.docx / 表格2；小鸡数值文档 / 表格2、表格3、4. 撞击概率计算；小鸡.docx / 2.1 完整游戏流程（通关阶段）；小鸡数值文档 / 3. 难度选择（表格2）
  - 风险分析：1、开发和测试无法确定真实的赔率表和概率公式，主流程无法编译和验收。；2、通关结算逻辑缺失，无法实现‘额外高额奖励’的发放，可能导致通关后收益不符合预期。
  - 修改建议：1、统一两份文档的难度定义。废弃需求文档中的简单难度4行数据，以数值文档的30关卡赔率表和CRASH公式为准，并在需求文档中补充说明‘具体难度与倍率映射见数值文档’。；2、在数值文档中补充‘超级大奖’的奖励规则（如：固定金额、奖池比例或额外倍率），并明确触发条件（如通过第30关）。
  - 关注角色：数值策划
  - 置信度：高
  - 阻塞级别：阻塞开发
- **[严重程度：中] 下注筹码配置示例与结构冲突**
  - 现状描述：需求文档示例筹码为3、5、10、20，数值文档示例为100、1000，两者不一致。
  - 证据来源：小鸡.docx / 表格1；小鸡数值文档 / 表格1
  - 风险分析：配置表结构不明确，开发可能按错误示例实现默认值。
  - 修改建议：统一配置表示例，明确筹码列表为可配数组，并给出默认推荐值（如[3, 5, 10, 20]）。

### 【可测试性与验收标准】
- **[严重程度：中] UI“被击中概率”展示口径与底层算法脱节**
  - 现状描述：UI界面显示‘被击中的概率’，但底层算法是CRASH公式（标准爆炸倍数）加上首次/非首次必撞概率（3%/1%），文档未说明UI上的概率值是如何计算和展示的。
  - 证据来源：小鸡.docx / 图片解析（图片1-8）；小鸡数值文档 / 4. 撞击概率计算
  - 风险分析：UI展示概率与实际结算概率不符，引发玩家客诉和信任危机，测试无法设计验收用例。
  - 修改建议：明确UI概率的计算公式（如：当前关卡的必撞概率 + 标准爆炸倍数小于当前关卡倍率的概率），或明确该概率仅为‘当前关卡基础必撞概率’的展示，并在UI上增加说明文案。
  - 关注角色：系统策划
  - 置信度：高
  - 阻塞级别：阻塞测试用例设计
- **[严重程度：中] 局内状态机与异常恢复（断线/重进/重复点击）规则缺失**
  - 现状描述：局内包含多次点击（前进、提现），文档未说明断线重连、重进、或在‘提现确认框’时退出的状态恢复规则。
  - 证据来源：小鸡.docx / 2.1 完整游戏流程、3.4 提现与结算系统
  - 风险分析：玩家可能在提现确认中退出以逃避失败，或断线重连后状态错乱，导致资金损失或客诉。
  - 修改建议：1、补充玩法专属异常规则：如断线重连后恢复当前局状态（保留已通关格数和倍率）；2、提现确认中退出视为放弃提现，继续游戏或默认失败；3、重复点击提现/开始需做幂等拦截。
  - 关注角色：系统策划
  - 置信度：高
  - 阻塞级别：阻塞测试用例设计

### 【安全性与反作弊】
- **[严重程度：低] 胜负判定机制的客户端/服务端边界冲突**
  - 现状描述：1、需求文档描述‘抵达马路后触发碰撞检测’、‘骆驼与车辆碰撞盒重叠即判定失败’，暗示客户端进行碰撞判定；2、但数值文档明确胜负由服务端CRASH算法（随机爆炸倍数+必撞概率）决定。；3、文档描述了‘点击开始进入游戏’、‘失败奖金清零’、‘提现获得当前总奖金’，但未明确开局时是否扣除本金、本金是冻结还是直接扣除，以及失败时是仅清零本局浮动奖金还是扣除本金。
  - 证据来源：小鸡.docx / 3.2 移动与碰撞系统；小鸡数值文档 / 4. 撞击概率计算；小鸡.docx / 2.1 完整游戏流程、3.4 提现与结算系统；小鸡数值文档 / 1. 游戏简介
  - 风险分析：1、若客户端负责碰撞判定，将导致严重的作弊风险（如修改碰撞盒）和结算不一致；2、服务端算法无法在客户端碰撞盒中体现。；3、结算链路无法实现，可能导致资金超发、玩家资产异常或财务对账失败。
  - 修改建议：1、明确服务端权威：服务端根据CRASH算法计算当前关卡是否被撞，下发结果给客户端；2、客户端仅根据服务端结果播放碰撞或安全通过的动画，取消客户端碰撞盒判定逻辑。；3、明确开局扣款时机（如点击开始时扣除本金并冻结），明确失败结算逻辑（如扣除本金，本局浮动奖金清零），明确提现到账目标（如钱包余额）。
  - 关注角色：系统策划
  - 置信度：高
  - 阻塞级别：建议优化

  - 关注角色：系统策划
