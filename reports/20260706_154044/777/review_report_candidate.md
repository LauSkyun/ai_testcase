## 优先处理事项
- **[高] RESPIN终止条件与乘数配置表数据缺失矛盾**
  - 责任建议：数值策划
  - 处理原因：1、程序在配置RESPIN随机池时找不到“空”的权重，导致RESPIN无法终止，形成死循环或报错。；2、测试用例无法覆盖自动旋转与RESPIN交互的边界情况，可能导致自动旋转提前终止或无限循环。；3、前端开发无法确定最终的动效标准，可能导致RESPIN在快捷模式下缺乏爽感或动画时间过长。
- **[高] RESPIN结算公式举例与数值规则存在严重数学冲突**
  - 责任建议：数值策划
  - 处理原因：1、核心结算公式存在致命歧义，程序若按举例实现会导致赔付放大10倍，造成严重资损；2、若按公式实现，则需求举例错误，测试验收无标准。
- **[高] 基础与RESPIN权重配置全为100，概率无差异，RTP无法控制**
  - 责任建议：数值策划
  - 处理原因：所有事件等概率，无法实现预期的RTP，无法进行数值调控，游戏无法正常运作。
  - 问题来源：副评审补充 (deepseek-v4-pro)

## 二、逐维度问题清单
### 【清晰度与完整性】
- **[严重程度：高] 基础符号“any”系列定义与盘面权重表逻辑倒置且互斥**
  - 现状描述：需求与数值文档将“any”、“any bar”、“any 7”等组合判定结果直接作为“最终盘面呈现的结果”并配置权重（表2）。同时定义存在交叉，如“2个any bar+1个任意7”既涉及any bar又涉及any 7，且文档声明“盘面不会同时满足多个条件”。
  - 证据来源：疯狂777需求文档修改后.docx / 段落10-14；crazy777数值文档修改后.docx / 段落9-14、表格2
  - 风险分析：将组合结果作为基础权重表会导致程序无法通过传统的转轮（Reel）随机生成盘面。若采用直接按结果权重RNG，则“any”系列的互斥定义在代码实现时极易出现边界遗漏或概率计算错误。
  - 修改建议：1、明确盘面生成机制：是采用“独立转轮随机+连线判定”还是“直接按组合结果权重RNG”。若是前者，需将表2改为具体符号（如7, bar, bar2, 空）在各列的出现权重；2、若是后者，需重写“any”系列的互斥判定逻辑，确保所有盘面情况穷举且概率和为100%。
  - 关注角色：系统策划
  - 置信度：高
  - 阻塞级别：阻塞开发
- **[严重程度：中] 金额缩位展示“向下取整”的边界计算规则不严谨**
  - 现状描述：文档规定金额缩位展示“保留两位小数向下取整”，举例15555显示15.55K。但未明确“向下取整”是针对最终结果还是中间过程，且未说明0或极小值的展示规则。
  - 证据来源：疯狂777需求文档修改后.docx / 段落30
  - 风险分析：开发在实现时可能使用四舍五入或不同的截断逻辑，导致客户端展示金额与服务端实际结算金额在视觉上产生微小偏差，引发玩家对“吞钱”的质疑。
  - 修改建议：补充明确的数学公式，例如：`display_value = floor(actual_value / 1000 * 100) / 100`，并补充小于1000时的展示规则（如直接显示整数）。
  - 关注角色：系统策划
  - 置信度：高
  - 阻塞级别：阻塞测试用例设计

### 【逻辑一致性与数值平衡】
- **[严重程度：高] RESPIN终止条件与乘数配置表数据缺失矛盾**
  - 现状描述：1、数值文档明确说明“在respin时一旦随机到空，则不再进入重转”、“本次重转值必定为空（0）→respin结束”。但RESPIN每次乘数值设定表（表7）中仅有1,2,3,5,10，未配置0（空）。；2、文档说明自动旋转“RESPIN结算完成后停止”，但未明确RESPIN期间的多次重转是否消耗自动旋转次数，以及RESPIN结束后是继续自动旋转还是直接停止。；3、需求文档描述快捷旋转下“省去特殊轴旋转效果，直接显示单次倍数叠加结果”，但紧接着又说“快捷旋转下RESPIN的表现：是快速播放累加动画”。
  - 证据来源：crazy777数值文档修改后.docx / 段落46、61、表格7；疯狂777需求文档修改后.docx / 段落35；疯狂777需求文档修改后.docx / 段落36
  - 风险分析：1、程序在配置RESPIN随机池时找不到“空”的权重，导致RESPIN无法终止，形成死循环或报错。；2、测试用例无法覆盖自动旋转与RESPIN交互的边界情况，可能导致自动旋转提前终止或无限循环。；3、前端开发无法确定最终的动效标准，可能导致RESPIN在快捷模式下缺乏爽感或动画时间过长。

  - 关注角色：数值策划
  - 置信度：高
  - 阻塞级别：阻塞开发
- **[严重程度：高] RESPIN结算公式举例与数值规则存在严重数学冲突**
  - 现状描述：1、需求文档举例：基础奖金10，特殊轴转4次(2,1,5,空)，最终金额=10*10*(1+2+1+5)=900。而数值文档公式为：中奖金额=基础投注×赔率×累加乘数。若基础投注=1，赔率=10，累加乘数=9，结果应为90。举例中多乘了一个10。；2、需求文档举例中的计算逻辑（10*10*9=900）与数值文档定义的公式（基础投注×赔率×累加乘数）存在10倍的数学偏差，导致核心结算链路无法对齐。
  - 证据来源：疯狂777需求文档修改后.docx / 段落19；crazy777数值文档修改后.docx / 段落30、43
  - 风险分析：1、核心结算公式存在致命歧义，程序若按举例实现会导致赔付放大10倍，造成严重资损；2、若按公式实现，则需求举例错误，测试验收无标准。
  - 修改建议：1、统一结算公式。建议修正需求文档举例为：基础投注10，赔率10，基础奖金100，累加乘数(1+2+1+5)=9，最终金额=100*9=900。或明确“基础投注奖金”的具体含义。；2、数值策划需重新核算并举例验证RESPIN结算公式，确保需求文档的举例与数值文档的公式完全一致。

  - 置信度：高
  - 阻塞级别：阻塞开发

  - 关注角色：数值策划

  - 现状描述：数值文档规定“超过100倍→直接强制0倍（123列至少一列为空）”。但未说明该风控是在基础局判定阶段生效，还是在RESPIN累加后生效。若RESPIN累加后超100倍（如777*10倍=770倍），强制0倍意味着玩家看到RESPIN动画但最终0奖励。

### 【可测试性与验收标准】
- **[严重程度：低] 推展机制的客户端表现与服务端结果对齐验收缺失**
  - 现状描述：1、需求与数值文档说明推展机制是“先得到最终结果，再进行表演（先展示空，再推展到乘数）”。但未说明在推展动画播放期间若发生断线，重进后是直接展示最终结果，还是重播推展动画。；2、需求文档侧重于推展的UI动效表现（回推/下拉），数值文档侧重于触发条件（倍数>5倍，概率2000）和底层逻辑（先出结果再表演）。两者未明确“结算倍数”是指基础赔率还是包含乘数后的总赔率，且未说明推展表演期间的断线恢复规则。
  - 证据来源：疯狂777需求文档修改后.docx / 段落44；crazy777数值文档修改后.docx / 段落39
  - 风险分析：测试无法设计断线重连的验收用例，可能导致重进后表现异常或状态机卡死。同时，结算倍数定义不清会导致触发条件实现错误，影响玩法核心逻辑。
