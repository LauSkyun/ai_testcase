# 需求文档分析报告

## 一、总体评价
需求文档对核心玩法循环、UI交互和题材包装描述清晰，但数值文档存在严重问题，直接套用了Crash游戏的连续爆炸公式，与需求文档的离散关卡跳跃模型产生根本性冲突。此外，两份文档在下注筹码、难度定义等基础配置上存在明显矛盾，且缺乏真钱博弈必备的结算与异常恢复规则。

- **文档质量评分：** C
- **评分原因：** 核心数值算法（Crash连续模型）与玩法模型（离散关卡跳跃）存在根本冲突，且双文档在基础配置上矛盾，需重构数值模型并统一配置后方可开发。

## 优先处理事项
- **[高] 核心数值算法与离散关卡玩法模型存在根本冲突**
  - 责任建议：数值策划
  - 处理原因：Crash公式生成的是全局崩溃点，无法与30个离散关卡的固定倍率表直接兼容。程序无法确定是按固定关卡倍率实现，还是按Crash连续曲线实现，导致核心玩法无法落地。；通关阶段的结算逻辑缺失，程序无法实现通关奖励的发放，测试无法验收通关结算。
- **[高] 下注筹码与难度配置在两份文档中完全矛盾**
  - 责任建议：系统策划
  - 处理原因：开发和测试无法确定最终的配置表字段、枚举值及默认值，导致前后端配置解析不一致。；阻塞配置表结构设计与前后端联调。
- **[高] 真钱博弈核心链路（扣款、结算、断线恢复、幂等）缺失**
  - 责任建议：系统策划
  - 处理原因：缺乏异常恢复和幂等说明，直接开发可能导致断线后状态丢失、重复扣款或重复派奖等严重资损事故。

## 二、逐维度问题清单
### 【清晰度与完整性】
- **[严重程度：高] 下注筹码与难度配置在两份文档中完全矛盾**
  - 现状描述：1、需求文档定义下注筹码为3/5/10/20，难度为简单/中等/困难/极限；2、数值文档定义下注挡位为100/1000，难度为24倍盘/62倍盘/103倍盘/176倍盘。两份文档的基础配置完全不一致，导致开发无法确定最终的配置表结构和读取逻辑。
  - 证据来源：小鸡.docx / 表格1、3.1 下注系统；小鸡数值文档.docx / 表格1、表格2、表格3
  - 风险分析：1、开发和测试无法确定最终的配置表字段、枚举值及默认值，导致前后端配置解析不一致。；2、阻塞配置表结构设计与前后端联调。
  - 修改建议：1、统一两份文档的配置口径。明确最终配置表中的筹码列表、难度枚举名称（建议保留简单/中等等用户向命名，将倍率盘作为后台配置参数），并补充完整的配置表示例。；2、统一两份文档的配置口径，明确最终配置表中的筹码列表、难度枚举名称，并补充完整的配置表示例。
  - 关注角色：系统策划
  - 置信度：高
  - 阻塞级别：阻塞开发
- **[严重程度：高] 核心数值算法与离散关卡玩法模型存在根本冲突**
  - 现状描述：1、需求文档描述的是离散关卡跳跃模型（每过一关乘一个固定倍率，共30关），但数值文档第4章直接套用了Crash（火箭）游戏的连续爆炸倍数公式（MAX_MUL/随机数），并提到“不超过就一直可以成功”。；2、需求文档提到“成功通过所有预设马路，触发超级大奖，获得额外高额奖励”，但数值文档的表格仅到第30关的基础倍率，未定义超级大奖的额外奖励数值。
  - 证据来源：小鸡.docx / 2.1 完整游戏流程、2.2 详细规则；小鸡数值文档.docx / 4. 撞击概率计算、表格2；小鸡.docx / 2.1 完整游戏流程、3.4 提现与结算系统；小鸡数值文档.docx / 3. 难度选择
  - 风险分析：1、Crash公式生成的是全局崩溃点，无法与30个离散关卡的固定倍率表直接兼容。程序无法确定是按固定关卡倍率实现，还是按Crash连续曲线实现，导致核心玩法无法落地。；2、通关阶段的结算逻辑缺失，程序无法实现通关奖励的发放，测试无法验收通关结算。
  - 修改建议：1、废弃Crash公式。针对离散关卡模型，重新设计概率算法（例如：为每个关卡配置独立的碰撞概率，或生成一个全局碰撞关卡索引，玩家到达该关卡前均安全）。；2、在数值文档中补充超级大奖的奖励规则（如：固定金额、额外倍率乘区、或奖池比例），并明确其与第30关基础倍率是叠加还是替换关系。
  - 关注角色：数值策划
  - 置信度：高
  - 阻塞级别：阻塞开发

  - 修改建议：统一UI倍率与数值配置，明确UI截图中的倍率是最终设计还是过时示意，并确保最终实现的倍率序列与数值文档表格2严格对齐。
  - 关注角色：数值策划
  - 置信度：高
  - 阻塞级别：阻塞测试用例设计
  - 问题来源：副评审补充 (deepseek-v4-pro)
- **[严重程度：中] UI展示的“被击中概率”缺乏可计算的数值映射**

  - 证据来源：小鸡.docx / 图片1-8；小鸡数值文档.docx / 4. 撞击概率计算

  - 修改建议：在数值文档中补充“被击中概率”的明确计算公式，确保UI展示值与服务端真实概率严格对齐，并说明该概率是单关概率还是累计概率。
  - 关注角色：数值策划
  - 置信度：高
  - 阻塞级别：阻塞测试用例设计

## 三、核心测试点建议
### 功能验证
- 验证不同难度下，30个关卡的倍率累乘计算是否准确。
- 验证提现功能是否正确结算当前累计奖金并清零局内状态。
- 验证失败（被撞）后奖金是否正确清零并返回准备界面。
- 验证通关（通过30关）后是否正确触发并发放超级大奖。
### 异常操作
- 验证在前进动画播放中断线重连，是否能正确恢复到断线前的关卡状态。
- 验证在结算动画播放中断线重连，是否能正确显示结算结果且不重复发奖。
- 验证快速连续点击“开始”和“提现”按钮，是否触发幂等保护，不产生重复扣款或派奖。
- 验证余额不足时点击“开始”，是否有明确的拦截提示。
### 兼容性
- 验证不同分辨率和刘海屏下，底部控制面板（筹码、难度、按钮）是否正常显示且不遮挡核心游戏区域。
### 安全专项
- 验证碰撞判定结果是否由服务端权威下发，客户端修改本地碰撞盒或加速是否能作弊通关。
- 验证提现接口是否具备幂等性，防止并发请求导致重复提现。
### 回归影响
- 验证修改难度配置或倍率表后，历史已生成的对局记录是否受影响。
### 性能与稳定性
- 验证车辆随机刷新和碰撞检测在长时间运行下是否存在内存泄漏或帧率下降。
### 用户体验
- 验证“被击中的概率”UI展示值是否与当前关卡的实际判定概率一致。
- 验证倍率数字跳动动画和提现反馈是否流畅，无卡顿。
