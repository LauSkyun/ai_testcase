## 二、逐维度问题清单
### 【清晰度与完整性】
- **[严重程度：中] Luck（随机扰动）的定义和生成规则缺失**
  - 现状描述：需求文档和数值文档中的T公式均包含Luck（随机扰动）因子，但未定义其取值范围、分布类型和生成时机。
  - 证据来源：musee游戏Racing.docx / 段落36；Racing数值文档.docx / 图片3
  - 风险分析：Luck直接影响每辆车的完成时间，进而影响胜负和赔率（若采用数值模型），缺失定义导致开奖算法不可实现且不可重现，测试无法验收。
  - 修改建议：在数值文档中补充Luck的详细规则：取值范围（如0.8-1.2）、分布类型（均匀或正态）、是否受奖池状态或干预逻辑影响，以及每局生成时机。
  - 关注角色：数值策划
  - 置信度：高
  - 阻塞级别：阻塞开发
  - 问题来源：副评审补充 (deepseek-v4-pro)
- **[严重程度：中] T（完成时间）公式中多段地形的累加逻辑未明确**
  - 现状描述：需求说明赛道分3段，每段L=100m，且每段地形随机。数值公式为 T = L / [V × K × Luck]。但未说明总比赛时间T_total是三段T值直接相加，还是有其他计算规则。
  - 证据来源：musee游戏Racing.docx / 3.4开奖逻辑 段落36；Racing数值文档.docx / 图片3
  - 风险分析：无法准确计算最终比赛耗时和排名，导致开奖逻辑无法实现。
  - 修改建议：补充多段地形的总耗时计算公式，明确 T_total = T1 + T2 + T3，并说明每段地形随机生成时的计算时序。
  - 关注角色：数值策划
  - 置信度：高
  - 阻塞级别：阻塞开发
- **[严重程度：中] MAX下注逻辑与单选项上限的边界行为存在歧义**

  - 风险分析：开发实现时可能产生歧义，导致用户预期不符或出现超投漏洞，阻塞测试用例设计。
  - 修改建议：明确MAX按钮在余额>100万时的具体行为：建议修改为“MAX按钮实际下注金额为 min(当前余额, 100万-当前选项已下注额)”，并补充相应的UI提示文案。
  - 关注角色：系统策划
  - 置信度：高
  - 阻塞级别：阻塞测试用例设计

### 【逻辑一致性与数值平衡】
- **[严重程度：高] 赔率计算核心公式存在两套冲突逻辑**
  - 现状描述：1、需求文档定义实时赔率为资金池比例算法（合计下注/本选项下注*系数）；2、而数值文档给出的公式为基于速度、地形、干扰指数的动态赔率算法（Odds_X = (T * (1-r) / W_X) * γ，且有最低赔率1.02）。两套逻辑完全独立且冲突。需求提到通过调整“干扰指数”来侧重开某车，干扰指数会影响T（完成时间）。但如果赔率是按需求文档的“资金池比例”计算，调整T对赔率没有影响；3、如果是按数值文档公式，调整T会改变赔率。
  - 证据来源：musee游戏Racing.docx / 3.3下注部分 段落28；Racing数值文档.docx / 图片1、段落3；musee游戏Racing.docx / 3.4开奖逻辑 段落40-44
  - 风险分析：开发无法确定最终采用哪套公式，直接阻塞核心结算链路开发。干预逻辑可能无法达到预期的控赔效果，导致奖池失控或用户体验极差。
  - 修改建议：1、统一赔率计算模型。若采用数值文档的竞速模型，需说明需求文档中的资金池比例公式是用于何处（如仅用于展示预期收益）；2、若采用资金池模型，需说明数值文档公式的作用。明确干预逻辑（调整干扰指数/地形概率）如何具体影响最终赔率和开奖结果，补充干预状态下的赔率重算规则。
  - 关注角色：数值策划
  - 置信度：高
  - 阻塞级别：阻塞开发
